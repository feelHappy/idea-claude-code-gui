# 开发流程选择规则

> 根据改动范围自动选择快速通道或完整流程。

---

## 流程路径

| 路径 | 适用场景 | 流程 |
|------|---------|------|
| **快速通道** | 单文件 bug 修复、配置/常量调整、文案修改、≤2 个文件的小改动 | 直接改 → 构建验证 → 提交 |
| **完整流程** | 新功能开发、涉及多文件/多层的改动、接口或表结构变更 | 八阶段流水线 |

---

## 快速通道判定条件（全部满足）

1. 改动文件 ≤2 个
2. 不涉及公共接口/API 签名变更
3. 不涉及数据库表结构变更
4. 改动意图明确，无需需求澄清
5. 可逆、低风险

---

## 完整流程总览

```
① 需求分析 → ② 需求评审 → ③ 任务拆解 → ④ 执行前检查
→ ⑤ 编码实现 → ⑥ 编码评审 → ⑦ 构建验证 → ⑧ 交付确认
```

### 人工确认点（3 个）

| 确认点 | 阶段 | 确认内容 |
|-------|------|---------|
| ✅ 确认点 1 | ② 需求评审通过后 | 计划摘要：需求范围、技术方案、影响面 |
| ✅ 确认点 2 | ⑥ 编码评审通过后 | 评审发现、关键修改、风险评估 |
| ✅ 确认点 3 | ⑧ 交付确认 | 交付摘要：变更文件、完成状态、遗留事项 |

---

## 分支命名规范

```
{type}/{需求编号}-{简述}

type: feat | fix | refactor | docs | chore
示例: feat/REQ-001-user-auth
```

---

## Commit 规范

```
{type}({scope}): {简述}

type: feat | fix | refactor | docs | style | perf | test | chore
scope: 模块名或功能域
示例: feat(auth): 添加 JWT token 刷新机制
```

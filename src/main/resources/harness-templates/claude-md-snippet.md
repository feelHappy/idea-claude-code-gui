## 冷启动序列（每次会话必须执行）

> 以下步骤在**任何开发任务开始前**执行，无论快速通道还是完整流程。

1. 检查 `_bmad-output/planning/` 目录是否有进行中的任务
2. 如果存在 `progress.md` 且最后一条是 `[下一步]` → 恢复该任务，从上次中断处继续
3. 新任务 → 立即创建 `_bmad-output/planning/{编号}/progress.md`，写入 `## [YYYY-MM-DD] 目标简述`
4. 读取 `.harness/rules/development-flow.md` 判断快速通道 or 完整流程
5. **功能演化追踪**：从用户请求 + 当前打开文件 + 最近 progress 提取功能关键词，用 GitNexus query 识别涉及的功能模块，查 `.harness/traces/index.md` 精准匹配对应 trace。匹配到则读取了解演化历史；匹配不到则跳过。

**跳过此序列 = 违规。即使是"改一行代码"也必须执行。**

## 反馈回路与自动验证

- **构建验证**：完成一个逻辑单元的代码修改后执行构建命令
  - 构建通过：不向用户输出任何内容，继续下一步
  - 构建失败：只输出错误行和错误信息，立即修复
- **循环检测**：同一文件修改 3 次以上仍未解决 → 停止，汇报卡点，提出替代方案
- **交付前验证**：完成一个 Story 后，对照验收条件逐项检查
- **进度追踪**（强制执行）：**每次开发任务（含快速通道）都必须记录进度**。追加到 `_bmad-output/planning/{需求编号}/progress.md`：
  - **会话开始时**：追加 `## [YYYY-MM-DD] 目标简述`
  - **完成一个逻辑单元后**：追加 `- [完成] 做了什么（涉及哪些文件）`
  - **遇到阻塞时**：追加 `- [阻塞] 问题描述和解决方案`
  - **会话结束前**：追加 `- [下一步] 还剩什么` + `变更文件：` 列表
  - 文件不存在时直接创建。格式简洁，每条一行即可。
  - **trace 联动**：如果本次改动满足 trace 触发条件（设计决策变更、状态模型变更、Bug 暴露设计缺陷、重构改变内部模型、推翻或修正历史 trace 中的方案），在 progress 中标注 `[trace: {功能名}]` 并更新对应 trace 文件。
- **会话结束验证**（强制执行）：结束前检查 `progress.md` 是否已更新。如果未更新，立即补写。
- **知识沉淀检查点**（强制执行）：以下任一条件满足时，**必须**执行知识沉淀评估：
  1. 构建失败 ≥2 次（同一问题）
  2. 方案发生变更（推翻了初始方案）
  3. 单次排查超过 10 轮工具调用仍在排查同一问题
  4. 会话 >5 轮（本次会话是否产生了新的模式/坑/决策？）
  5. 用户说"收工"/"完成"/"提交"时
  
  **评估动作**：读取 `.harness/playbooks/index.md`，判断本次经验是否匹配已有 playbook：
  - 匹配 → 追加新条目到对应 playbook
  - 不匹配但满足提取条件 → 新建 playbook
  - 不满足 → 静默跳过
  
  **沉淀后**：追加一条记录到 `.harness/log.md`。

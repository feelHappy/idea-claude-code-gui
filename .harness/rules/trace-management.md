# 功能演化追踪规则

> Trace 只记录会影响未来判断的功能级决策，不记录流水账。

---

## 硬规则（三条，无例外）

1. **Trace 只记录会影响未来判断的功能级决策，不记录流水账。**
2. **每条 trace 必填 `关联任务`（progress 路径）；`关联提交` 提交后补齐；`证据来源` 可选。**
3. **冷启动通过 GitNexus 识别相关功能，再读取 `traces/index.md` 精准匹配；匹配不到不强行读 trace。**

---

## 需要写 trace 的场景

| # | 场景 | 判断标准 |
|---|------|---------|
| 1 | 新功能交付 | 完整流程走完、功能上线 |
| 2 | 修改了设计决策、状态模型、流程边界、并发/缓存/异步策略 | 功能的"骨架"变了 |
| 3 | Bug 根因暴露了设计缺陷或历史决策问题 | 不只是修 bug，而是发现设计有问题 |
| 4 | 重构改变了内部模型，未来维护者不知道原因会踩坑 | 即使对外行为不变 |
| 5 | 推翻或修正了历史 trace 中的方案 | 在旧 trace 条目上标注 `[已修正]` 并链接新条目 |

**一句话判断法**：如果下次有人改这个功能，不知道这次的决策会踩坑吗？会 → 写。不会 → 不写。

---

## 不需要写 trace 的场景

- 纯格式化、命名微调、注释修正
- 局部实现替换，未来维护者不需要知道决策背景
- 测试补充且不改变功能设计
- 机械迁移且已有 progress 足够说明

---

## Trace 条目格式

```markdown
### [YYYY-MM-DD] {变更标题} — {需求编号或"快速通道"}

- **动机**: 为什么要改（一句话）
- **决策**: 选了什么方案，放弃了什么，为什么
- **变更前状态**: 改之前的关键行为/模型（简述，不贴代码）
- **变更内容**: 改了什么（设计层面，不是文件列表）
- **影响面**: 这次改动影响了哪些其他功能
- **与上次的关系**: 扩展 / 修正 / 重构 / 推翻
- **关联任务**: `_bmad-output/planning/{编号}/progress.md`
- **关联提交**: {commit hash，提交后补齐}
- **证据来源**: {可选：issue、复现步骤、GitNexus impact 结果、用户反馈}
```

---

## Trace 文件结构

```markdown
# Feature Trace: {功能名}

## 元信息
- **涉及核心文件**: 列出主要文件路径
- **所属模块**: 模块名
- **创建时间**: YYYY-MM-DD
- **最后更新**: YYYY-MM-DD

## 演化时间线

### [日期] 条目 1 ...
### [日期] 条目 2 ...
```

---

## 与 progress.md 的关系

| 维度 | progress.md | trace |
|------|-------------|-------|
| 组织方式 | 按任务/会话 | 按功能模块 |
| 回答的问题 | "今天做了什么" | "这个功能为什么是现在这样" |
| 记录粒度 | 每个逻辑单元 | 只记录设计级决策 |
| 互相引用 | trace 条目中填 progress 路径 | progress 中标注 `[trace: xxx]` |

---

## 冷启动增强

新会话恢复时，在现有冷启动序列之后追加：

```
3. 从用户请求 + 当前打开文件 + 最近 progress 提取功能关键词（关键词只作为 GitNexus query 输入，不写入 index）
4. 用 GitNexus query 识别涉及的功能模块
5. 查 .harness/traces/index.md 匹配对应 trace
6. 匹配到 → 读取该 trace，了解功能演化历史
7. 匹配不到 → 跳过，不强行读取
8. 如果本次修改与历史决策冲突 → 主动提醒用户
```

---

## 维护规则

- **不一次性补写历史**：已有功能的 trace 按"下次碰到时补"原则，触碰时再写
- **不存代码快照**：代码状态交给 Git，trace 只记录 commit hash + 为什么
- **膨胀控制**：单个 trace 文件超过 50 条时，归档旧条目到 `{name}-archive.md`
- **过时标记**：如果某条 trace 被后续条目推翻，标注 `[已修正 → 见 YYYY-MM-DD 条目]`
